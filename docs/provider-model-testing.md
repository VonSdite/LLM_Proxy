# Provider 模型测试口径

核对日期：2026-11-15。当前实现位于 `src/services/provider_model_test_service.py`，请求经过 `src/services/upstream_request_builder.py` 和协议转换器。以下结论来自代码审阅与模拟上游回归，未请求真实付费上游。

## 时间与用量

| 项目 | 当前实现 | 适用范围与限制 |
| --- | --- | --- |
| 首字延迟（TTFT） | 请求准备完成、调用上游 executor 前记录 `perf_counter()`，首个非空 `content` 或 `reasoning_content` 完整到达时计算时间差 | 包含连接、网络及上游等待，不含请求构建、Hook 和代理参数准备。忽略空角色、心跳和用量事件。思考片段同样计入，不保证是首个正文；重试只展示成功尝试的时间。 |
| TPS | `completion_tokens / 总秒数`，等价于 `completion_tokens × 1000 / duration_ms` | 全程平均输出速度，包含首字等待、思考及末尾用量、终止事件等待；本次成功尝试从调用上游开始计时，不含请求准备和先前失败尝试。 |
| 数据块时间 | 每次接收到非空网络数据块时记录单调时钟，块内事件共享时间 | 首字延迟以能够解码完整内容事件的数据块到达时间为准；TPS 使用完整请求时长。 |
| 无法计算 | 输出用量缺失、输出为零、总时长无效或测试失败时，TPS 为空 | 单个输出 Token、单数据块、隐藏思考和非流式成功响应均可计算 TPS。非流式 TTFT 仍为空，界面显示 —。 |
| 思考用量 | 输出 Token 遵循上游 usage，已包含的推理 Token 不重复相加 | 思考过程是否在流中可见不影响公式。 |
| 可用状态 | 有正文或推理片段且未发现错误即为成功 | 不验证复制内容是否完整，也没有把正常结束标记作为成功的必要条件；仅证明本次请求收到有效模型输出。 |

例如请求在第 0 秒发起，首个输出在第 2 秒到达，末个正文在第 4 秒到达，用量及结束事件在第 20 秒完成，上游报告输出 100 Token：TTFT 为 2000ms，TPS 为 `100 / 20 = 5 Token/s`。

系统使用上游 usage 的输出 Token，不通过字符数、SSE 事件数或数据块数推算用量。网络、等待、思考和响应缓冲均影响全程平均速度。

## 实际请求

基础请求使用 `stream=true`、`max_tokens=192`，省略 `temperature` 和 `top_p`，采用上游默认采样行为；提示模型原样复制 12 行固定英文文本。固定输出内容有助于减少任务差异；较短的输出上限适合低成本可用性检查。

- OpenAI Chat：保留基础字段，补充 `stream_options.include_usage=true`。
- Responses：输出上限转换为 `max_output_tokens`。
- Claude：使用 `max_tokens`。
- 模型名含 `glm` 的 Claude 接口：额外设置 `reasoning_effort=low`，转换为 `thinking={type: enabled, budget_tokens: 2048}`；总输出上限为 2240，思考预算以外保留 192 Token 额度。预算由协议转换器的同一辅助函数计算。
- 使用当前表单中的认证、指定 Auth Entry、代理、证书校验、超时、最大尝试次数和请求 Hook；Hook 可以继续修改实际请求。测试产生的成功用量会写入请求日志，包含成功状态、HTTP 状态、流式标记、首字延迟、总耗时、TPS 和缓存明细。缓存解析复用统一 usage 合并器，明确的零值与未报告字段分别保存。

GLM Claude 是当前基准请求中唯一按模型名启用的特判；其他模型的思考策略采用上游默认行为。192 Token 对需要较长思考的模型仍可能不足，参数名兼容不代表已经识别所有模型的思考需求。

### 参数自适应

OpenAI Chat 在 HTTP 400 或 422 的错误信息明确表示 `max_tokens` 不受支持且指出 `max_completion_tokens` 时，会在下一次尝试中替换输出上限字段，额度保持不变。字段替换发生在 translator 和请求 Hook 之前，Hook 继续具有最终请求控制权。

每个模型测试最多进行一次字段切换，与普通重试共同遵守 `max_retries` 总尝试次数；值为 1 时仅发出一次请求。切换结果仅用于当前模型的后续尝试，不缓存到其他模型、Provider 或后续测试。认证失败、模型不存在、额度范围错误及未明确指出替代字段的错误继续按原错误返回。成功测试只记录一次用量。

[OpenAI 官方 Chat Completions 文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) 将 `max_tokens` 标为已弃用，指出其不兼容 o 系列模型；`max_completion_tokens` 的额度包括可见输出与思考 Token。本项目同时服务多种兼容上游，字段切换依据实际错误信息，不依赖模型名或别名推断。

## 与 Sub2API 的对应

[Sub2API 的 formatUsageOutputRate](https://github.com/Wei-Shaw/sub2api/blob/530c5e3a4f9c73ca2b0881191d0ef8e0d82c5484/frontend/src/utils/latencyHealth.ts#L73) 使用输出 Token 乘以 1000 再除以总耗时毫秒。本项目的 Provider 测试、模型映射测试和请求统计均采用这一公式。

该指标表示单请求全程平均输出速度。生成阶段吞吐量和整个服务的并发总吞吐量属于不同指标。统计页面的平均 TPS 是成功请求中有效 TPS 的算术平均；请求统计总耗时包括代理处理和内部重试，模型测试显示本次成功尝试的耗时。

## 后续建议

1. 默认测试提供可用性、首响应体验和全程平均速度参考；严格跨模型比较时保持输出类型与用量口径一致。
2. 模型需要更长思考时，根据确认的能力信息为思考预算与正文输出分别预留额度；字段兼容和预算规划分开处理。
3. 需要严格性能比较时，使用更长的统一输出、多次采样和中位数，并区分首个推理片段与首个正文片段。
4. 精确的逐 Token 解码速度需要服务端 Token 时间戳或明确的分块 Token 计数；客户端接收间隔仅提供近似。

界面使用“结果、首字延迟、TPS”独立列，错误信息位于操作列。表头问号与模型映射测试详情共用说明文案，列出公式、单位、思考范围和 — 的条件。模型测试回归覆盖协议请求、参数兼容、GLM 预算、全程平均速度公式、跨协议一致性、分块计时和隐藏思考边界。架构未变化。

模型测试日志从该模型测试开始计时，包含准备与重试，首字时间和总时长使用同一起点；弹窗性能展示本次成功上游尝试。重试时用量收集状态独立，成功记录不包含失败尝试的缓存字段或首字时间。未采集性能和缓存明细的历史记录保留未知。
